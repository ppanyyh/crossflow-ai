# CrossFlow AI｜跨境电商售后智能协同工作台

> 一个面向跨境电商售后团队的桌面端协同 Demo：将英文客户售后消息推进为**可解释、可审批、可质检、可追溯**的处理结果。

> **作品集项目 / 模拟业务数据 / 非生产系统**。不连接真实订单、物流、支付、退款或客户数据；已完成一次可选的真实 DeepSeek 草稿生成联调，但不将模型用于最终业务决策。

## 1. 为什么做这个项目

跨境售后客服常常需要在客户英文消息、订单与物流事实、售后规则、主管审批之间反复切换。单纯的 AI 聊天助手可以起草回复，却难以回答几个关键问题：

- 这条回复是否与订单和物流事实一致？
- 客户要求退款或补发时，AI 是否越权承诺？
- 高风险问题由谁审批、如何留下处理记录？

CrossFlow AI 的目标不是让 AI 自动执行退款或补发，而是把 AI 放在受控协同流程中：**AI 做理解与建议，人做风险决策，规则做最终门禁。**

## 2. 目标用户与首期场景

| 角色 | 核心需求 | 在系统中的操作 |
| --- | --- | --- |
| 一线客服 | 快速理解问题、获得合规英文草稿 | 查看事实与建议、编辑回复、创建工单 |
| 客服主管 | 控制退款/补发等高风险决策 | 查看规则依据、审批并留痕 |
| 售后运营 | 观察处理效率、风险与质量 | 查看运营看板与问题分布 |

MVP 覆盖英文客户的物流延误、严重物流停滞与退款施压、签收未收到、订单号缺失等售后场景。

## 3. 核心设计：人机协同而非 AI 越权

```text
客户英文消息
    ↓
订单 / 物流事实 + 售后规则
    ↓
AI 决策卡：意图、情绪、风险、命中规则、回复草稿
    ├─ 低风险：客服编辑/发送 → 已解决
    ├─ 信息不足：请求订单号 → 待客户补充
    └─ 中高风险：创建工单 → 主管审批 → AI 质检 → 允许结案
                                                        ↓
                                               审计记录与运营看板
```

### 风险控制原则

- AI 仅可建议、归类、起草与创建待审核工单；
- 订单与物流事实来自结构化模拟数据，不由模型编造；
- 高风险、退款施压、签收争议、隐私类问题必须进入人工流程；
- 未经审批的中高风险案例不能结案；
- 中高风险案例即使审批完成，也必须质检通过才能结案；
- 系统不承诺退款金额、退款时效、补发已执行或确定送达时间。

## 4. 已实现能力

### 业务与交互

- 会话工作台：按状态、风险、国家、问题类型筛选；
- 三栏会话详情：客户与时间线、AI 分析与英文草稿、订单物流事实与工单操作；
- 高风险建单、主管审批、审计日志；
- 回复质检：事实一致性、未经授权承诺、主管审批前置条件、明确后续动作；
- 低风险直达结案、订单号缺失转“待客户补充”；
- 动态运营看板：已解决数、低风险可直达率、人工介入率、回复合规率、问题/风险分布；
- 基于 Axure 制作规范对齐的 1440px 桌面端界面。

### V1.6 可选 LLM 增强

- 通过 OpenAI-compatible 接口调用 DeepSeek，仅生成结构化信息提取与英文回复草稿；
- 默认关闭 LLM；未配置、超时、网络异常、非法 JSON 或安全校验失败时，自动回退确定性规则模板；
- 返回前预校验拦截越权承诺、错误订单号、虚构签收及业务决策字段；
- LLM 草稿仍须通过既有 AI 质检，且高风险案例仍必须经人工建单、主管审批与质检门禁；
- 已完成一次脱敏真实联调：`HTTP 200`、`source=llm`、`fallback=false`、草稿通过质检；不记录 API Key、请求内容或完整草稿。

### V2.1 关键门禁

```text
高风险案例
建单 → 主管审批 → 质检 overall_passed = true → resolve
```

上述约束由后端强制执行。若跳过质检直接结案，接口返回 `403`；质检失败会清除旧的通过标记，避免使用过期结果结案。

## 5. 技术架构

```text
┌──────────────────────────────────────────────┐
│ 浏览器前端                                    │
│ 原生 HTML / CSS / JavaScript / fetch          │
└───────────────────┬──────────────────────────┘
                    │ HTTP JSON
┌───────────────────▼──────────────────────────┐
│ FastAPI 后端                                  │
│ main.py：路由与静态前端挂载                   │
│ schemas.py：Pydantic 请求/响应数据模型        │
│ service.py：规则、状态机、质检、看板与预校验 │
│ llm_client.py：可选 DeepSeek 草稿生成         │
└───────────────────┬──────────────────────────┘
                    │
┌───────────────────▼──────────────────────────┐
│ 模拟业务数据                                  │
│ orders.json / logistics.json / rules / cases  │
└──────────────────────────────────────────────┘
```

- 后端：Python 3.12、FastAPI、Pydantic、Uvicorn、pytest；
- 前端：原生 HTML/CSS/JavaScript，不依赖构建工具；
- 数据：本地 JSON；进程重启后会话状态与工单状态复位；
- AI：默认使用确定性规则与安全模板；可通过本地 `.env` 启用 DeepSeek 草稿增强，失败自动回退且不改变业务决策权。

## 7. 本地运行

### 前置条件

- Windows + Python 3.12；
- 项目已包含用于本地演示的 `backend/.venv` 虚拟环境。

### 启动 LLM 增强版（推荐演示）

在 PowerShell 中执行：

```powershell
cd "F:\跨境电商售后智能协同工作台\07_LLM增强Demo\backend"
.\.venv\Scripts\python.exe -m uvicorn main:app --reload --port 8001
```

浏览器访问：

- 工作台：<http://127.0.0.1:8001/>
- 接口文档：<http://127.0.0.1:8001/docs>

`backend/.env` 未配置或 `LLM_ENABLED=false` 时，LLM 接口会自动回退规则模板；启用 DeepSeek 的 Key 仅保存于本机 `.env`，不会进入代码或文档。停止服务请在终端按 `Ctrl + C`。服务重启后，内存中的工单与会话状态会复位，这是 Mock Demo 的预期行为。

### 运行冻结的纯 Mock 基线

若需演示不依赖外部 LLM 的 V2.1 基线，使用 `06_可运行Demo/backend` 并启动到 `8000` 端口即可。

## 8. 自动化验证

```powershell
cd "F:\跨境电商售后智能协同工作台\07_LLM增强Demo\backend"
.\.venv\Scripts\python.exe -m pytest tests -v
```

当前结果：**37 passed**。

测试覆盖：

- 高风险建单与重复建单幂等；
- 低风险不能建单、可直接结案；
- 高风险未建单/未审批/未质检时禁止结案；
- 订单号缺失进入“待客户补充”；
- 主管审批同步更新工单与会话状态；
- 回复质检识别错误订单号、未经授权承诺和未审批高风险；
- 质检通过后结案，以及质检失败后清除旧通过状态；
- 列表筛选、看板数据、404 与响应结构。
- LLM 未启用、超时、非法 JSON、安全预校验降级、英文缩写排版规范化；
- 真实 LLM 草稿仍被质检与高风险结案门禁约束。

## 9. 推荐演示路径

1. 打开高风险案例 `CF-DEV-002`：物流停滞 12 天且客户要求退款；
2. 查看订单、物流事实与命中规则，创建人工审核工单；
3. 主管选择“批准补发建议”；
4. 未质检时尝试结案，展示系统返回的质检门禁；
5. 可选点击“使用 LLM 重新生成草稿”，确认其来源标签为“LLM 生成，需客服复核”；
6. 对英文草稿运行质检，四项通过后发送并结案；
7. 打开运营看板，展示已解决数变化；
8. 补充演示 `CF-DEV-001` 低风险直达和 `CF-DEV-004` 订单号缺失分支。

## 10. 项目边界与下一步

本项目不接入真实 Shopify、Amazon、ERP、物流商、支付系统或真实客户数据；不执行真实退款、补发或订单修改；不实现生产级登录、权限、多租户与消息推送。

当前 LLM 增强版仍不连接真实业务系统，不执行退款、补发或订单修改。后续如需扩展，应继续保持“LLM 只做理解与草稿、规则决定风险与门禁、人工承担最终决策”的架构边界。
