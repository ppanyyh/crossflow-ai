# CrossFlow AI V4 Mock Backend

> **重要声明：本服务是模拟数据驱动的作品集原型（Portfolio Prototype），不是生产系统。**
> 所有订单、物流、客户、案例均为 `data/` 目录下的模拟 JSON，不连接真实 Shopify、Amazon、物流商、支付系统、客户数据或任何外部大模型 API。所有指标（看板数据等）均为模拟计算结果，不代表真实业务表现。

## 1. 项目说明

跨境电商售后智能协同工作台（CrossFlow AI V4）的独立 Mock 后端，实现 `docs/API_CONTRACT.md` 定义的全部接口。

- **技术栈**：Python 3.12 · FastAPI · Uvicorn · Pydantic v2
- **数据源**：仅读取项目根目录 `data/` 下的模拟 JSON（`cases_dev.json`、`orders.json`、`logistics.json`、`after_sales_rules.json`）
- **数据路径**：由代码文件位置计算（`service.py` → `../../data`），与终端当前工作目录无关
- **无外部依赖**：不依赖 V3 项目，不需要任何 API Key，AI 决策由案例预期结果 + 售后规则确定性生成（可复现、可演示、可测试）
- **不做危险承诺**：接口永不返回自动退款、自动补发、保证到货时间或赔偿金额

## 3. 环境准备与启动

```bash
cd "F:\跨境电商售后智能协同工作台\06_可运行Demo\backend"

# 创建虚拟环境（Python 3.12）
python -m venv .venv

# 激活（Windows PowerShell）
.venv\Scripts\Activate.ps1
# 或 Git Bash
source .venv/Scripts/activate

# 安装依赖
pip install -r requirements.txt

# 启动服务（默认 http://127.0.0.1:8000）
python -m uvicorn main:app --reload --port 8000
```

**启动后用浏览器访问 <http://127.0.0.1:8000/> 即可打开前端工作台**（frontend 目录由后端以静态文件方式挂载到根路径 `/`，无需任何前端构建步骤或额外服务器）。

- 前端工作台：http://127.0.0.1:8000/
- 交互式接口文档（Swagger UI）：http://127.0.0.1:8000/docs

## 4. 前端操作说明（V2 · 对齐 Axure 规格）

工作台为单页应用（桌面 1440px 风格），顶部 64px 白色栏 + 左侧 240px 深色导航（工作台 / 会话 / 工单 / AI 质检 / 运营看板），所有数据均通过 fetch 实时调用本服务 API，前端不硬编码任何业务结果。

1. **工作台**：待处理 / 待人工审核 / 高风险会话 / 今日已解决四张指标卡（可点击筛选跳转）、高风险待办列表、效率卡（AI 建议采纳率 / 人工介入率 / 回复合规率）。
2. **会话**：左侧状态与风险筛选面板，右侧表格（客户 / 国家 / 摘要 / 风险 / 状态 / 案例），支持国家与问题类型辅助筛选。
3. **会话详情（三栏 320/500/340）**：左栏客户信息 + 会话状态 + 时间线；中栏客户消息 + AI 分析 + 可编辑英文草稿 + 质检入口；右栏订单物流事实 + AI 决策建议 + 工单操作。隐私/他人订单（L-08）自动隐藏订单事实并显示安全提示；签收争议展示签收记录与证据提示。
4. **高风险主流程（Axure 串联）**：会话详情 →「创建人工审核工单」520px 弹窗（预填原因/风险/推荐处理/优先级）→ 工单中心 → 主管审批（三栏：订单物流事实 / AI 建议与规则 / 主管操作四选一）→ 回到会话详情编辑回复 → AI 质检 → 确认发送并关闭 → 运营看板。高风险会话无「直接关闭」路径；**审批后必须「AI 质检通过（quality_passed）」，操作区才会出现「发送回复并解决」按钮（后端同样强制，见第 7 节）**。
5. **AI 质检**：独立页面，可选任意案例 + 回复运行四项规则质检；质检不通过时不得关闭会话；质检通过后会写入该案例的内存 `quality_passed` 标记，作为中/高风险结案门禁；通过后若会话可解决则显示「确认发送并关闭会话」并跳转看板。
6. **运营看板**：成功提示条 + 四张指标卡 + 售后问题环形图 + 风险等级横向条形图（全部来自 `GET /api/dashboard`）。

## 7. 已实现接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查（契约外附加） |
| GET | `/api/cases` | 会话列表，支持 `status`、`risk_level` 过滤 |
| GET | `/api/cases/{case_id}` | 会话详情（404 如果不存在） |
| POST | `/api/tickets` | 创建人工审核工单（仅 `handoff_required=true`；重复创建幂等返回现有工单） |
| GET | `/api/tickets` | 工单列表，支持 `status` 过滤 |
| POST | `/api/tickets/{ticket_id}/approve` | 主管审批，工单与会话状态变为 `处理中`，写入 `audit_log` |
| POST | `/api/cases/{case_id}/resolve` | 低风险发送回复→`已解决`；订单号缺失→`待客户补充`；中/高风险未审批返回 403；中/高风险已审批但未质检通过（`quality_passed=false`）返回 403 |
| POST | `/api/quality-check` | AI 质检：订单/物流事实一致、无未经授权承诺、高风险已审批、包含后续处理说明；`overall_passed=true` 时写入该案例内存 `quality_passed` 标记，否则清除 |
| GET | `/api/dashboard` | 运营看板（`simulated: true`） |
| GET | `/`（静态） | 前端单页工作台（frontend/index.html） |

### 状态机

```
待处理 ──创建工单──▶ 待人工审核 ──主管审批──▶ 处理中 ──AI 质检通过(quality_passed)──▶ 已解决（工单→已关闭）
   │
   └──request_order_information──▶ 待客户补充   （订单号缺失案例）
```

中/高风险案例在「处理中」状态下，若未通过 AI 质检（`quality_passed=false`）直接调用 `resolve` 会返回 403。低风险与订单号缺失分支不经过该门禁。

## 8. 已知限制

1. **纯内存状态**：会话状态与工单保存在进程内存中，重启即复位；没有数据库持久化。
2. **AI 决策为确定性模拟**：基于 `cases_dev.json` 的预期结果与售后规则生成，不调用任何大模型；对契约外的新话术不会有真实理解能力。
3. **质检为规则引擎**：未授权承诺检测基于关键词/正则模式（退款金额、退款承诺、补发已执行、保证送达时间等），存在误报/漏报可能。
4. **中风险也要求审批后才能 resolve**：契约只定义了低风险可直接解决、高风险未审批不得解决；本实现对 `handoff_required=true` 的中风险案例采取与高风险一致的保守策略。
5. **质检门禁 `quality_passed` 为内存标记**：与状态机一样随进程复位；该标记仅表示「最近一次质检整体通过」，不持久化、不替代真实质检系统。建单、审批推进到「处理中」、以及重新质检未通过时，该标记会被清除。
6. **无鉴权**：Mock 服务不区分客服/主管身份，任何调用者均可执行所有操作。
7. **审批后不执行动作**：主管审批仅记录决策（如"批准补发建议"），系统不执行真实退款/补发，也不会在回复中承诺执行结果。
8. **看板指标为模拟计算**：基于当前 14 条案例数据与内存状态计算，数值随操作变化，仅用于演示。
9. **英文回复为主**：回复草稿模板为英文（与案例数据语言一致），未做多语言生成。
10. **前端为单页 Mock Demo**：界面文案中已显著标注"模拟数据 / 非生产系统"；不做登录、权限或多人协作。
